## 3. Findings

### F1 — PassphraseAdvisor initialization order (HIGH, fixed in `c4de3ce`)

`GUARANTEED_BITS` and `WORD_COUNT` were declared *before* `WORDS` but read it
in their initializers. Kotlin initializes object members in declaration
order, so this is the compile error *"Variable 'WORDS' must be initialized"*.
CI caught it on `901a3e3` (`:security:policies:compileKotlin FAILED`); the
sandbox static audit could not have caught it without a compiler, which is
precisely why the push→CI→fix loop is part of this repository's definition of
done. Fix: `WORDS` now precedes both derived properties; the unit test pins
`WORD_COUNT == 512` so the list cannot silently drift.

### F2 — Wrong floor-case expectation in the advisor test (MEDIUM, fixed in `4efe856`)

`estimateBits is zero for empty and floors at zero` asserted
`estimateBits("     ") == 0`, but five spaces score 25 − 20 = 5 bits
(single character class + identical-run penalties) — the value is positive,
so the assertion failed and, with it, `:security:policies:test`. Only an
input whose raw estimate minus penalties goes negative exercises the
`coerceAtLeast(0)` floor: `"aaaa"` (18 − 20 = −2 → 0) now carries that case,
and the test comment records why five spaces do not.

### F3 — Pre-existing unused string resources (INFO, no action)

`action_share`, `contacts_add`, `contacts_title`, `sheet_from_manual` are
defined but unreferenced from Kotlin. Three further candidates
(`process_text_encrypt_label`, `process_text_decrypt_label`,
`share_decrypt_label`) are used by `AndroidManifest.xml` activity labels —
not dead. All seven predate v0.4.0; removal was deliberately left out of
scope.

### F4 — Deferred forward reference in `ProtocolRandom.SECURE` (INFO, no action)

`val SECURE = RandomSource { … SECURE_RANDOM.nextBytes(it) }` reads
`SECURE_RANDOM`, which is declared after it. Legal — the read happens inside
a lambda that runs only after the object is fully initialized — but it is
the fragile cousin of F1's bug pattern. Recorded for awareness; the new
forward-reference audit check now distinguishes the two forms (direct read =
error, deferred lambda = warning).

## 4. The v0.4.0 behavior contract (what was manually reviewed)

1. **Old-key-era decryption** — an envelope whose keyId belongs to a
   superseded era resolves through the session manager's bounded LRU
   historical cache (≤ 8 entries, wiped on eviction, expiry, `lock(contact)`
   and `lockAll`). No historical session yet → `NeedsEraUnlock`, the UI
   collects the passphrase of THAT era, `unlockEra` re-derives and verifies
   it against the era's wrapped digest verifier (same honest-error contract
   as `unlockContact`: infrastructure failures are `Failed`, never a false
   "wrong passphrase"). A historical key is *never* visible to
   `activeSession` lookups and never used for encryption.
2. **Stale-active-session guard** — a latest-era envelope is never decrypted
   with an active session that predates the rotation (previously a
   guaranteed AEAD failure); it now asks for a fresh unlock.
3. **Verifier step deduplicated** — `unlockContact` and `unlockEra` share
   `verifyAndPersistVerifier`; the extraction preserves the original
   behavior (v1→v2 migration rewrite, best-effort first-unlock persist,
   `stored.fill(0)` after the check, lock-on-infrastructure-failure in
   `unlockContact` only).
4. **Biometric stays latest-era-only** — a fingerprint wrap is bound by AAD
   to the contact's *current* era; era prompts therefore never offer it
   (`biometricOffered = false`).
5. **Passphrase advisor** — the meter is display-only (enforcement stays
   with `KeyPolicy`); the generator draws 7 words + 2 ASCII digits
   (`Locale.ROOT` — locale-stable across devices) for 69 guaranteed bits on
   top of the Argon2id KDF cost. The recommendation card appears only when
   the new-contact dialog is creating a key (blank invite), is never stored,
   and is copied through the `ClipboardAccess` chokepoint.
