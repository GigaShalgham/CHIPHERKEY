# CipherKey Deep-Scan Audit — 2026-11-05

**Scope**: full repository at commit `b7c555b` (branch `004-samsung-companion-fixes`,
tag `v0.2.1-alpha`), all 15 modules, ~6,100 lines of main Kotlin + ~2,500 lines
of test code, documentation, release artifacts, CI, and build health.

**Method**: machine-verified rebuild of the toolchain (JDK 21.0.13+9, Gradle
8.13, Android SDK 36 / build-tools 36.0.0) followed by `gradle test` and
`gradle assembleDebug` from a cold cache; static scans (secrets, permissions,
logging, TODO markers); module-by-module code review of every main-source
file; spot re-verification of every MEDIUM-severity finding against the code;
artifact verification of the released v0.2.1 APK (`sha256sum`, `apksigner
verify --print-certs`, `aapt2 dump badging`); documentation cross-check
against the implementation.

---

## 1. Executive summary

The cryptographic core and overall engineering discipline are **sound**. The
scan found **no CRITICAL and no HIGH severity issues**: AES-256-GCM is used
correctly with fresh 96-bit nonces bound as AAD together with the full
55-byte header; Argon2id parameters match the documented profiles and
reproduce the RFC 9106 known-answer vector; the wire format is strict; no
secrets, no logging, no network code, and no Android permissions exist
anywhere in the tree.

Twelve MEDIUM findings exist, concentrated in three areas: (a) a real but
low-probability race that can persist a corrupted unlock verifier and
permanently reject the correct passphrase for a key era; (b) honest-labeling
gaps in the shipped UX (Keystore infrastructure failures reported as "Wrong
passphrase", decrypt notices headed "Encrypt", no `FLAG_SECURE` on screens
that display decrypted plaintext); and (c) documentation drift — the README
still describes the v0.1 keyboard-centric architecture and the v0.1.0 test
count (140) rather than the shipped v0.2.1 companion architecture (187).

Two **environment findings** are more consequential than any code finding:
the GitHub PAT and the release signing keystore were both lost with the
build sandbox and are not recoverable locally (see §5).

## 3. Findings — shipped code (app APK v0.2.1)

Severity scale: CRITICAL (exploitable crypto break) > HIGH (likely data loss
or security regression) > MEDIUM (real defect, bounded impact) > LOW (polish)
> INFO (observation).

### MEDIUM

1. **Unlock-verifier race can permanently reject the correct passphrase.**
   `KeySessionManager.activate()` stores `keyBytes` **by reference**
   (`core/sessions/.../KeySessionManager.kt:83`; `keyId`/`salt` are correctly
   `copyOf()`-defended). On first unlock, `MessageCipher` calls
   `sessions.activate(...)` and only afterwards persists
   `protector.wrap(derived, ...)` (`data/repository/.../MessageCipher.kt:133-148`)
   — outside the manager's mutex. A concurrent `lock()`/`lockAll()` (the
   "Lock all sessions now" control) zeroes the same array mid-wrap and can
   persist an **all-zeros verifier**: every future unlock of that era fails
   with `WrongPassphrase` (recoverable only by era rotation or clearing app
   data). Fix: copy the buffer in `activate()` (or wrap before activating).
2. **Keystore failures are misreported as "Wrong passphrase".**
   `AndroidKeystoreKeyProtector.unwrap()` catches all exceptions
   (`security/storage/.../AndroidKeystoreKeyProtector.kt:63`), and
   `unlockContact` maps every `KeyProtectionException` to
   `UnlockOutcome.WrongPassphrase` (`MessageCipher.kt:152-155`) even though
   `UnlockOutcome.Failed` exists. A KeyStore infrastructure error (e.g.
   master-key invalidation after a system update or `KeyStoreException`)
   instructs the user to retype a perfectly correct passphrase. There is no
   key-invalidation recovery path and the cached `SecretKey` handle is never
   evicted.
3. **No `FLAG_SECURE` on activities that display decrypted plaintext.**
   Zero occurrences in `app/src/main` (grep-verified). `noHistory` +
   `excludeFromRecents` protect the recents preview but not screenshots or
   screen recording (`CompanionUi.kt:328-341` renders plaintext).
4. **Decrypt-side failure notices are headed "Encrypt".**
   `CompanionUiState.mode` defaults to `ENCRYPT`
   (`app/.../CompanionViewModel.kt:43`); early notice paths preserve the
   default, so an empty/oversized **decrypt** invocation shows the header
   "Encrypt" (`DecryptActivity.kt:38-43`, `ShareDecryptActivity.kt:31-36`,
   clipboard-failure paths).
5. **Stored "verifier" is the full session key, not a digest.**
   `storeWrappedKey(era.sessionId, protector.wrap(derived, era.keyId))`
   persists the complete derived AES key (Keystore-wrapped) although it is
   only ever read back for an equality check
   (`MessageCipher.kt:148`, `Entities.kt:60`). A keyed digest would give
   identical wrong-passphrase rejection with strictly less exposure: with
   the DB plus the app's Keystore key (rooted/forensic device) all traffic
   decrypts without the passphrase. The stored key is never functionally
   reused, so this is pure added risk.
6. **Contact-creation errors render behind the add-dialog scrim.**
   Failures (e.g. "Invalid invite code") are written to the home-screen
   feedback column while the dimmed `AddContactDialog` stays on top
   (`ContactsScreen.kt:83-90` vs `:117-127`); the dialog itself shows
   nothing. Errors are effectively invisible at the moment they happen.

### LOW / INFO (shipped code)

7. [LOW] Settings screen stale copy: "You can always lock immediately from the
   keyboard toolbar" references the IME removed from the shipped app in v0.2
   (`SettingsScreen.kt:52`); the About card still reads "CipherKey 0.1.0"
   against `versionName = "0.2.1"` (`SettingsScreen.kt:104`).
8. [LOW] Session expiry is lazy (no timer): an expired-but-unqueried key stays
   in memory until process death (`KeySessionManager.kt:94-102`).
9. [LOW] `KeyProtector` fingerprint formatting uses `String.format("%03d", …)`
   with the default locale — Persian-locale devices render fingerprints with
   Persian digits, breaking text comparison of this out-of-band verifier
   (`core/keys/.../KeyProtector.kt:37,44`; use `Locale.ROOT`).
10. [LOW] Companion notice text renders twice (notice card + unconditional
    error line, `CompanionUi.kt:114-120`, `:393-396`).
11. [LOW] `BaseCompanionActivity.onNewIntent` handles a "singleTop relaunch"
    that no manifest activity declares — dead code as configured
    (`BaseCompanionActivity.kt:84-90`).
12. [LOW] No try/catch around crypto/repo calls in the companion flows; an
    unexpected exception crashes the process with `busy=true` UI frozen
    (`CompanionViewModel.kt:140-172` et al.).
13. [LOW] Timeout slider writes to DataStore on every drag frame
    (`SettingsScreen.kt:57-62`; write on `onValueChangeFinished` instead).
14. [LOW] "Copy invite" bypasses the `ClipboardAccess` chokepoint (raw
    `ClipboardManager`), swallows failure, gives no feedback
    (`ContactsScreen.kt:337-342`).
15. [LOW] `deleteContact` cleans the era cache but not the fingerprint cache
    (`ContactsViewModel.kt:133-140`).
16. [LOW] Latest-era selection orders only by `createdAt`; same-millisecond
    eras are nondeterministic (`Daos.kt:36`). `importEra` is check-then-act
    on the unique `keyId` index (`SessionKeyRepository.kt:63-84`).
17. [INFO] Clipboard copy of decrypted plaintext has no auto-clear and does
    not set `EXTRA_IS_SENSITIVE` (Android 13+); the THREAT_MODEL residual-risk
    wording on clipboard plaintext should be kept aligned with this behavior.
18. [INFO] The documented "wipe on field switch / service destroy" is not
    implemented in the IME; unlocked keys survive until timeout/manual lock
    (relevant only if the IME ships again — see §4).
19. [INFO] Passphrase `String`s in Compose dialogs cannot be zeroed (toolkit
    limit, documented); only the derived `CharArray` copies are wiped.
20. [INFO] `PassphraseCryptoProvider.encrypt` throws on unsupported mode while
    `decrypt` returns a typed failure — inconsistent error surface.

## 4. Findings — dormant `:keyboard` library (built + tested, NOT shipped in the APK)

The v0.2 companion architecture (spec 003) does not register an input method;
`:keyboard` is compiled and unit-tested as a library only
(`settings.gradle.kts` includes it; `app/build.gradle.kts:109` deliberately
excludes the dependency). Findings below matter **only if the IME is
re-introduced**:

21. [MEDIUM] `replaceAll` is not atomic (no `beginBatchEdit`/`endBatchEdit`):
    if `deleteSurroundingText` succeeds and `commitText` fails, the user's
    draft is deleted with no insertion and no rollback
    (`InputConnectionTextField.kt:41-63`).
22. [MEDIUM] `readDraft()` concatenates before+after cursor text and
    **excludes the active selection** — encrypting with a selection silently
    omits it; select-all yields "Nothing to encrypt" (`:65-70`). `null`
    (unreadable) is conflated with empty via `.orEmpty()`.
23. [MEDIUM] Draft reads of up to 100,000 chars per side (~400 KB over
    Binder) run synchronously on the main dispatcher although CK1 caps
    plaintext at 16 KiB (`:74`, `CipherKeyboardService.kt:66,89`).
24. [LOW] `lockActiveContact` does not clear the decrypted preview
    (`ImeController.kt:233-240`).
25. [LOW] `KeyboardLifecycleOwner` dispatches only ON_CREATE/ON_DESTROY; safe
    today, silently incompatible with any future
    `collectAsStateWithLifecycle` usage (`CipherKeyboardService.kt:79,120`).
26. [LOW] `isSensitiveField` live re-check (`TextFieldAccess.kt:31`) is never
    consulted in production — unused defense-in-depth. (The canonical
    AOSP sensitive-field set — password/visible-password/web-password and
    numeric password variations — IS correctly enforced at both render and
    action time, with a test proving clipboard suppression.)

## 7. Current unlock behavior (baseline for the planned authentication work)

The maintainer has planned unlock/UX improvements (biometric unlock,
passphrase-only unlock, configurable keep-unlocked duration). The scan
establishes the precise current baseline from the code:

- The passphrase is requested by the IME dialog, the app contacts screen,
  or the companion activity — all funneling into
  `MessageCipher.unlockContact(contactId, passphrase)`.
- On unlock: Argon2id derivation off the main thread → (if a verifier
  exists) Keystore unwrap + constant-time compare → session activation for
  a **non-renewing timeout** (DataStore-configurable, 60 s–1 h, default
  5 min) → on first unlock the wrapped verifier is persisted.
- Within the timeout, encrypt/decrypt use the cached session key with **no
  re-prompt**; re-entry happens after timeout, process death, era rotation,
  or manual lock. (The perception "every operation asks" comes from IME
  process restarts plus the fixed, non-sliding window.)
- Consequences for the planned work: the session manager already provides
  the timeout/lock scaffold a biometric gate needs; the race in §3.1 and
  the error-conflation in §3.2 should be fixed **before** adding biometric
  unlock, since both sit directly on the unlock path.

## 8. Recommended actions (priority order)

1. Re-provision the GitHub PAT and back up the signing keystore off-machine
   (or generate + disclose a new one) — these block all release operations.
2. Fix §3.1 (copy `keyBytes` in `activate()`) and §3.2 (surface
   `UnlockOutcome.Failed` for Keystore errors) — small, testable, and they
   harden the exact path the planned authentication work will extend.
3. Add `FLAG_SECURE` to the companion activities and fix the decrypt-notice
   mode header (§3.3, §3.4) — small UX/honesty fixes in shipped code.
4. Replace the stored verifier with a Keystore-wrapped **digest** (§3.5);
   requires an era-level or app-level migration — schedule with spec 005.
5. Update the README to the v0.2 companion architecture and the 187-test
   reality; fix the stale Settings copy and About version (§3.7, §6).
6. Only if the IME returns: make `replaceAll` atomic, include the selection
   in `readDraft`, cap draft reads at the 16 KiB protocol limit (§4).
